## Architecture and Implementation Boundaries

The server accepts and owns definitions. The common, side-safe canonical guide model enters `StageDefinition` from both stage representations, proceeds through parser and schema 4 compiled display metadata, and is copied into the existing immutable definition entry. The editor owns only draft presentation and targeted source edits. It must apply through the existing validated review/apply APIs, preserve comments and unknown future keys, retain existing `stage.description` without migration, and leave unsaved draft work recoverable on stale revision or rejected input.

The exact `[guide]` schema is `guide.how_to_unlock`, `guide.next_steps`, `guide.where_to_find`, and `guide.recommendation`. The first three are strings defaulting to `""`, each independently limited to 2048 Unicode code points and 8192 UTF-8 bytes. Recommendation is the string enum `auto`, `include`, or `exclude`, default `auto`. Parser, draft validation, field counter, encoder, and decoder enforce the same code-point and byte limits. Reject invalid encoding, a control character other than line feed, carriage return, or tab, wrong type, unknown recommendation enum, and an oversize value with its source key. Never silently truncate stored content.

Guide content is inert Unicode multiline text. Preserve its line breaks, whitespace, authored language, and literal formatting markers. It cannot execute commands, interpret HTML, create click events, format as a command, or navigate externally. Whitespace-only values stay preserved but count as empty only for the auto recommendation decision. Unknown future guide keys remain source-preserved and have no executable meaning.

The server sends the same accepted guide values through `NetworkHandler.sendStageDefinitionsSync`, `StageDefinitionEntry`, and `handleStageDefinitionsSyncClient` to `ClientStageCache.StageDefinitionData` and `StageTreeScreen`. Keep the existing server-supplied `hasTriggers:boolean` field intact through both consumers. `auto` is true only for an otherwise qualifying stage with `hasTriggers` or a nonblank guide field. Do not transfer private trigger definitions, client-infer integrations, or create a second mutable guide authority. The client is presentational and cannot grant a stage, reveal content, or make a server permission decision.

The main config `general.enable_stage_guide` follows master IF-003: strict Boolean, default true, server controlled, not a stage-form or player-menu toggle. Add its accepted value to both protocol 3 display consumers through the existing snapshot revision owner. A main config load or supported reload schedules a new accepted snapshot even when stage text is unchanged. Reject invalid policy updates without replacing the last accepted state. A local COMMON config cannot override the server. Clear policy on disconnect and treat guide availability as false until the current complete snapshot arrives. Preserve descriptions, authored fields, ownership and unlock behavior while disabled.

Protocol registration changes from 2 to 3. Protocol 2 peers fail negotiation with a useful mismatch before positional bytes are decoded. A complete full snapshot has a nonnegative accepted definition revision and atomically replaces client definition and guide state only after validation. Reload, grant, revoke, team state, and screen refresh recompute candidates from that accepted snapshot and current authoritative ownership. Reconnect clears stale definitions before a complete current snapshot. Do not compare unrelated revision counters.

Preserve existing payload and definition limits; add explicit validation of the encoded definition payload against the transport's actual maximum before send. If the new fields make a supported pack exceed that maximum, bounded chunking under protocol 3 is required instead of silent omission, client crash or a new arbitrary stage count limit. Chunks carry definition revision, zero based index and total count; bound count and cumulative bytes to the validated full snapshot size, discard incomplete or superseded assembly after 200 client ticks, and apply only after complete validation. The phase verifies the pinned transport limit from source, records it in tests and documentation, and does not assume a limit from another Minecraft version. Existing valid packs with empty guides remain loadable.

Recommendation begins with existing hidden/reveal visibility policy, then unowned state and existing ANY, ALL, or AT_LEAST prerequisite satisfaction. `exclude` always removes a candidate. `include` overrides only the recommendation filter and never visibility. `auto` uses only the declared trigger bit or nonblank guide condition. Qualifying branches sort ascending by `uiSortOrder`, category, display name, then stage ID with locale-independent comparison and stage ID final tie break. Render the `What to do next` tab and `Prerequisites met`, never a forced unique next stage or a promise of immediate unlock. Reuse existing slot, cost, and trigger information to explain acquisition conditions, retaining author text and server validation. Selecting a candidate focuses its existing node and inspector in the guide tab. A normally visible selected stage may show its guide while owned or excluded only when the server guide option is enabled. No guide, search result, cross reference, category summary, aggregate count, or empty state may leak hidden or unrevealed identities. Empty output says no suggested stages are available, never that all content is complete.

### Advancement style, tabs and input

Reuse the existing Minecraft advancement window texture, connected item-node map, backgrounds, font, inspector, search, categories, pan and zoom. Add top Stages and What to do next tabs without covering existing controls at compact scales. Stages retains the normal map. The guide tab emphasizes recommended nodes with normally visible prerequisite context and shows How to unlock, Next steps and Where to find in the same scrollable inspector. Preserve map position, selection, search and categories when switching tabs; returning to Stages focuses the selected visible node. Revalidate removed/hidden selections on accepted state updates. No separate dashboard skin, pack creator attribution, source footer or authoring banner appears in the UI or editor preview.

Register What to do next beside the existing stages key mapping in Controls. Keep it independently rebindable and unbound initially. Use the existing explicit open/request path with a guide-tab target; original commands, inventory button and stages key still target Stages. Drain queued presses, open once per tick, ignore typing in another screen or absent joined player, and prefer the normal Stages action if bindings conflict. Refresh only updates an open screen and retains its active tab; delayed responses cannot reopen a closed screen. Switching tabs never sends purchase or grant requests. When disabled, hide every guide section and its tab, make the guide key a no-op without a request, and return an already open guide to Stages while preserving valid map state. Reenable uses current accepted data.
