## Architecture and Implementation Boundaries

Release integration keeps one candidate identity across source, editor assets, metadata, broker preview, platform files, downloads, and runtime evidence. The candidate manifest records the merged `master` commit, phase tag, semantic version, JAR filename, SHA-256, SHA-512, Minecraft version, NeoForge version, existing dependency relations, source asset digest, packaged asset entries, and relevant sanitized configuration fingerprint. Candidate identity changes after any rebuild, metadata edit, dependency change, or source edit; invalidate downstream preview, publication, download, and runtime proof and rebuild from the changed merged candidate.

The release only changes the mod release version to 3.1.0 and actual release metadata. It rebuilds Vite assets through the existing repository path, runs `PackagedEditorAssetsTest`, and inspects the final JAR entries for `app.js` and `app.css`. In `editor-ui`, the candidate checks are `npm ci`, `npm run check`, `npm test`, and `npm run build`; the Java checks are `./gradlew test`, `./gradlew build`, and the relevant dedicated server GameTests after confirming their task graph remains headless. Inspect Gradle tasks and package scripts for a formatter before claiming formatter coverage because the observed build declares none. It preserves pinned platform and toolchain dependencies. Development GameTests do not substitute for production startup. The phase compares tested classes and packaged contents before production verification.

Documentation uses one fact source per behavior: IF-001 and IF-002 structure behavior, IF-003 and IF-004 guide data and protocol behavior, IF-005 defaults and editor behavior, and IF-006 diagnostic support behavior. Examples use exact accepted semantics rather than abstract promises. They explain that `entry_allowed=true` removes only its own entry denial and never creates ALLOW; protection-only stages can still deny configured placement; actorless explosion and spawning protection is structure scoped without a player; omitted priority preserves inherited behavior; an explicit zero differs from omission; and generic explicit ALLOW remains the advanced override path. Recovery instructs operators to back up and review exact existing files, diagnose source ownership, and apply explicit edits instead of deleting files by name.

Publication uses the configured broker only. First discover current supported operations. Then inspect state, replace the stale selected 3.0.4 artifact with the approved 3.1.0 merged candidate without touching unrelated root changes, and obtain a new preview. Bind that one current preview or required confirmation value to the exact project IDs, commit, version, release channel, filename, hashes, Minecraft 1.21.1, NeoForge, existing dependency relations, and both required Modrinth sides. Do not reuse a stale preview identifier, assume an `inspect-file` command, inspect credential values, call direct upload APIs, or add a publication target. A new destination, cost, license, or operation requires a specific owner decision before it occurs. After a platform accepts the candidate, preserve that public file, its exact bytes, its identity, and the signed release tag. Retry only a missing platform with the identical approved bytes. A defect requiring changed bytes or a changed version is a forward-correction decision: retain evidence and open gates, request exact owner authorization, and never replace, relabel, force-tag, or silently republish changed 3.1.0 bytes.

Post-publication evidence integration is distinct from the fixed source candidate. After P003-TASK-005 produces live public links, downloaded hash results, production and client receipts, final release notes, and completion records, create a documentation-only closing branch from then-current approved `master`. Commit, sign, and push only those tracked evidence and documentation updates, complete its required checks and private independent review, merge it through the checked pull request workflow, and verify the resulting `master` commit. Preserve the prior source candidate pull request, phase tag, artifact hashes, and accepted platform files. Wiki publication and issue 57 closure follow this documentation merge only.

The released JAR verification separates server-authoritative state, client-received state, browser interaction, and rendered menu evidence. The dedicated server proves production startup and server behavior. The laptop client proves only the named editor and menu presentation, guide refresh, and actual interaction claims. A server assertion, browser request, or tag cannot close a client visual gate. The shared diagnostics interface remains default off and remains a support feature after temporary evidence cleanup.
