## Proposed shared structure contract

Keep the existing structures.locked_entry exact-ID target list for compatibility. Add strict Boolean structures.rules.entry_allowed. Missing or false retains each stage's entry gate; true contributes no entry denial and does not create an ALLOW rule that can cancel another stage. Independently, a missing owner stage contributes configured break/place denial only on its listed structures. Owned stages stop contributing those player restrictions. Any matching active denial remains, unless an existing explicitly configured conditional/compiled override resolves under existing semantics. An unobtainable stage means one configured without grant mechanisms; do not add a special reserved stage ID or make administrator grants impossible.

Treat implicit chest/container and block/entity interaction restrictions as consequences of an active entry denial, not of merely being in a target list. Thus a protection-only entry_allowed=true stage does not invisibly block opening or interacting unless separately configured. Preserve existing provider/session arbitration and creative/spectator bypass rules. Scope padding to the actual denying entry contribution. Preserve the global block_structure_entry switch as the existing master control unless the owner explicitly requests a separate global switch.

Explosion and spawn events lack a meaningful player stage owner. Preserve their unconditional protection semantics, scoped to only the structures declaring those flags, and document that they are not per player stage unlocks. This is a compatibility detail that must be explicit in the master contract. Correcting global cross structure OR leakage changes unintended behavior: document it and test separate structures. Do not add wildcard/tag selector support while implementing this flag; reject or explain unsupported convenience-list selectors rather than silently accepting ineffective values.

Patch LegacyStageCompiler's synthesized structures.enter rule as well as the aggregate. Keep both old monolithic stage files and schema 4 packages consistent. Validate wrong type, omitted field, empty targets, duplicate/overlapping structures, repeated reload and rollback before publishing a candidate snapshot. Use immutable contribution snapshots, deterministic explanation ordering and no per-tick disk lookup.

## Defaults owner decision

The approved default policy leaves essential movement unrestricted. Retain the existing nonmovement showcase content unless independently required otherwise. Remove default jump, sprint, swim and climb restrictions; avoid surprising default elytra locks as a conservative supported-ability policy. New editor-created stages likewise start without ability locks. Administrators retain explicit opt-in ability restrictions. Do not add a new example import product flow merely to solve this. Existing files remain unchanged; explain and document explicit recovery for old generated movement restrictions. Cover both generation paths, restart and malformed discovery.

## Targeted editor contract

Use plain labels such as Stage name, Stage icon and Required stages, with brief Minecraft style hover tooltips explaining what a player sees and one relevant example. Keyboard focus and click or tap expose the same help; validation errors and save state remain inline. Retain serialized keys, identifiers, advanced controls, source editing and supported existing terminology where needed. This is not translation infrastructure or a rewrite.

Add visible actions next to selected graph nodes and a right-click menu with Edit, Connect, Duplicate and Delete from draft where supported. Reuse StageActions/StageDialogs and server draft validation. Provide keyboard context invocation and focus return, Escape/outside dismissal, a visible pointer alternative, viewport clamping and no accidental drag writes from right click. Connect through existing cycle prevention. Keep deletion confirmation and review/apply semantics. Do not silently enable destructive actions for legacy/archived stages when existing APIs reject them. Hidden stage visibility, full localization and new graph libraries are optional future proposals, not required expansion.

## Failure mechanisms and proof

- Ghost compiled entry rules can cancel the new flag. Parse through both legacy and schema 4 compilation, then exercise actual StructureEnforcer entry and place decisions before and after grant/revoke/reload.
- Global OR flags can leak between structures. Use two distinct structures with different stage owners and opposite flags; require no unrelated denial and unchanged results under registration order permutations.
- Protection-only stages can still cause bounce or chest locks. In the sponsor two stage fixture, grant only the entry stage, enter and open an allowed chest, then assert placement denial remains. Keep provider-deny negative cases.
- Actorless rules can accidentally select a nearby player's ownership. Test explosion/spawn with zero players and players with differing stages; outcomes remain scoped and deterministic.
- Startup and loader may regenerate defaults after deletion, archive or malformed config. Test empty, valid existing, invalid existing, package-only and restart states; invalid input must not be overwritten or interpreted as a fresh install.
- Graph gestures can mutate a dependency or position while opening a menu. Browser tests cover pan/zoom, drag, right click, keyboard, edge selection, close/cancel, delete confirmation, failed save and stale draft.
- Explain output may blame a compiled rule while legacy ability state blocks jump. The diagnostic record must identify actual evaluator, action, source path/key, owner stage, stage presence, contributors, override winner, provider/session reason and final decision. Record a bounded correlation/revision; do not expose private config or credentials.
- A build can pass while packaged editor assets are stale. Rebuild with the existing Vite path, compare packaged assets and run PackagedEditorAssetsTest plus exact jar inspection.

## Additional locked owner scope and priority design

Version is exactly 3.1.0. The owner requests optional configuration controls as part of the mod's configuration-driven behavior. Include structures.rules.priority as a strict integer default 0. It applies to active structure restriction candidates, never invents an ALLOW candidate from false, and participates in the existing deterministic priority comparison for the same structure and action. An entry_allowed=true stage contributes no entry candidate, at any priority; a separate entry gate still denies. Existing generic action specific ALLOW rules remain the explicit way to override lower priority deny rules. Equal-priority deny wins. Entry false or omitted retains an entry deny candidate while its stage is missing. Break/place true contributes its action deny while missing; false/omitted contributes nothing. Actorless explosion/spawn flags stay structure-scoped OR protection with no fabricated player and no priority-based allow mechanism. Document that boundary rather than advertising priority as universal.

Proof must include two deny stages, matching/nonmatching structures, equal and unequal priorities, a real generic ALLOW override above/below the convenience restriction, registration order permutation, stage ownership changes and compilation parity. Do not let LegacyStageCompiler duplicate a convenience candidate at a different priority. Keep signed bounded integer validation exact and reject overflow/type errors with source key diagnostics. Preserve existing field defaults and explain whether padding follows the final entry-denying contribution. No tri-state Boolean schema is needed because false means no optional protection; explicit allowing has an existing representation.

## Next-stage guide, mandatory CORE-REQ-009

The owner requires guidance in the actual in game stages menu, with custom editor fields explaining how to unlock a next stage, what to do and where to find objectives. Existing stage.description is general prose shown in the tooltip and inspector, not a dedicated next stage guide. Preserve it and add optional guide metadata with empty defaults, for example stage.guide/how_to_unlock, next_steps and where_to_find or a dedicated [guide] table after master schema selection. Avoid overloading general description or creating a quest engine. The exact key naming is an engineering decision that must be frozen consistently across parser, editor, packets, documentation and examples.

StageTreeScreen builds available as unowned and dependenciesSatisfied, then applies hidden/reveal filters. Availability is not proof that an administrator-only stage is obtainable. Use top Stages and What to do next tabs in the existing advancement style map and inspector, with a separate initially unbound guide key. Main config `general.enable_stage_guide` defaults true and supplies authoritative server policy; disabled guidance leaves the ordinary map and saved text intact. Omit pack creator attribution from the GUI and preview. The guide emphasizes visible, unowned progression candidates whose prerequisite policy is satisfied, with author instructions and a focus/select action. Use existing ANY/ALL/AT_LEAST dependency semantics and deterministic uiSortOrder, category, name, ID ordering. Preserve multiple branch choices rather than selecting a single forced path. Provide an explicit optional guide inclusion/exclusion field for manual only permanent protection stages; do not infer a reserved ID or claim external acquisition is impossible. Default recommendation policy must avoid presenting guidance free unobtainable lock sentinels as an actionable next step. Label candidates as stages whose prerequisites are met, not guaranteed instantly unlockable. Keep selected-stage guidance available when normally visible even if not recommended. Show no fabricated instructions when empty; use a concise empty-state message rather than claiming all content is complete. Costs/slots/conditions can explain why a candidate is not immediately claimable, without hiding the author's guide or bypassing server validation.

The flow is StageDefinition and StageFileParser -> NetworkHandler.sendStageDefinitions and StageDefinitionEntry -> handleStageDefinitionsSyncClient -> ClientStageCache -> StageTreeScreen.renderInspector and next-step selection. Schema4 compiled snapshots also carry display metadata; choose one canonical guide model and maintain both synced consumers without stale split state. NetworkHandler currently registers protocol string 2, and StageDefinitionEntry codec is positional. New fields require an explicit compatible extension or protocol bump with clear old-client rejection; never append bytes and claim old protocol compatibility. Reconnect, reload, revocation, team-state changes and screen refresh must update guidance from the same accepted revision.

Text is bounded inert multiline content, not commands, HTML or automatic external navigation. Use plain strings with safe rendering, sensible length limits, natural language and Unicode support, wrapping and scrolling at small GUI scales. Blank fields preserve existing packs and no guide may reveal hidden/unrevealed stages through next-step cards, search or cross-links. Editor preview must identify that actual stage state controls player visibility. Round-trip import/export, rename, duplicate, source preservation, invalid type/oversize input and unknown future fields are mandatory proof. Real silent laptop capture must show a branch guide, authored location text, grant/revoke refresh, hidden-stage absence and a long guide at compact scale.
