## Pinned source observations

1. StageFileParser.parseStructures reads structures.locked_entry and rules.prevent_block_break, prevent_block_place, prevent_explosions, disable_mob_spawning and entry_padding. No entry_allowed parser exists. Padding is clamped nonnegative and takes the larger value from the two accepted locations.
2. LockDefinition.StructureRules contains one CategoryLocks selector collection, four booleans and padding. LockRegistry.StructureRulesAggregate.merge stores exact structure ID to required stages, globally ORs flags and takes global maximum padding. Non-ID selectors are ignored by this aggregate, even though the parser accepts CategoryLocks. Do not silently promise tag, namespace or wildcard support for the proposed convenience table.
3. StructureEnforcer.evaluate uses aggregate entry stages to derive staticBlocked for every action. staticProtects gates break/place with aggregate booleans, permits no static item-use check, and treats entry/container/block/entity interaction as protected. The entire static section is under StageConfig.isBlockStructureEntry. Actorless explosion and mob spawning methods use global flags plus all entry IDs, independent of players or stage ownership. Candidate enumeration unions aggregate IDs with conditional structure target IDs.
4. LegacyStageCompiler.compile line 53 emits a structures.enter compiled lock for every legacy locked_entry. Schema4StageCompiler.compile starts from legacy output, then decorates priority and adds generic rules. Changing only the aggregate is insufficient: compiled entry locks would remain. ConditionalLockEngine.resolve combines static and compiled rules; higher priorities win and LOCK wins equal effect ties. Preserve existing explicit priority/conditional facilities rather than inventing a second priority key.
5. StructureContextRegistry and StructureAccessArbitration combine provider/session access with static denial. Provider permits do not erase static denial. Existing session validation checks owner, dimension, bounds, instance and access stage. Entry independence must not bypass these checks.
6. Progressivestages.generateDefaultStageFilesIfNeeded scans TOML at startup and writes DefaultShowcaseStages.files if none are found. StageFileLoader.initialize independently generates the same defaults after empty successful discovery. Both paths require coordinated behavior. DefaultShowcaseStages has 50 packages and 150 files. showcase:end_protocol rules include abilities("jump"); other showcase stages also gate abilities. These are active discoverable files, not inert examples. Existing stage files skip generation; changing generation alone does not repair old generated packs.
7. AbilityEnforcer rebuilds GATERS from configured abilities and sends changed lock sets to clients. LivingJumpEvent cancels positive vertical velocity when jump is blocked; ConditionalLockEngine also contributes. Empty ability configuration has no inherent jump lock. Do not delete the capability or silently override intentional admin rules to solve defaults.
8. EssentialsPanel labels are exactly Player facing name and Icon item. Icon help already says to choose a registered item. EffectsPanel already has Player abilities and Choose abilities, explaining locks remain until stage ownership. The improvement is discoverability and plain terms, not a missing basic ability editor.
9. LayoutPage is an existing custom SVG graph with pan, zoom, drag position persistence, connect mode, dependency-cycle checks and keyboard node/edge activation. A click selects the stage, edge click removes a prerequisite, and no node context menu exists. Pointer-up clears drag before click, so drag-versus-click suppression needs regression proof rather than assuming it is correct. Hidden/archived stages are filtered. StageActions already has duplicate, rename, archive, restore, export and delete confirmation through server draft APIs. Reuse these flows, especially destructive confirmation and review/apply.
10. Current master has newer TOML preservation helpers and editor/permission repairs absent from the root checkout. Reuse master helpers; do not overwrite them with root versions.
11. /stage explain target <category.action> <target> [player] resolves only compiled engine traces. It is not a complete explanation of legacy ability GATERS or actual structure/provider arbitration. Existing /stage debug interactions|progression|permissions|editor on <player>, status, off uses permission level 3 and bounded diagnostic infrastructure. Extend that infrastructure for actual decisions instead of calling current explain sufficient.
12. Current README and DOCUMENTATION contain structure/ability references but do not resolve the reporter workflow. DOCUMENTATION 4.16 describes flags across listed structures and global block_structure_entry covering entry, chest locking and flags. They must state new per stage/per structure composition and actorless semantics and give the exact two stage example. No blanket rewrite is necessary.
