# 3.0.4 Entity Presence Fixture

This procedure verifies the entity presence cache introduced for 3.0.4. It defines the controlled
test protocol and records the Phase 001 candidate capture. Attach the captured profiles, raw MSPT
samples, dedicated server log, source revision, and final verdict to the Phase 001 pull request
before treating the performance gate as complete.

## Environment

Use the same Minecraft 1.21.1 and NeoForge 21.1.219 environment for both runs. Use the candidate
server JAR, the same Java version, the same world seed, the same configured simulation distance,
the same player count, and the same entity population. Disable unrelated profiling and debug mods.
If Spark is used, use the same Spark version and profiler options for both captures.

Use two connected survival players in the same dimension and inside simulation distance of the same
mob population.

- The denied player has a stage or rule that denies skeleton `presence`.
- The eligible player does not own that stage and has no other skeleton presence restriction.
- The fixture contains enough skeletons and tracked entities to exercise normal tracking repeatedly.
- Record the exact stage files, player stage ownership, simulation distance, entity count, warmup
  length, sampling duration, candidate commit, and JAR hashes before each capture.

### Raw sample collector

For this fixture only, start the dedicated server with the following JVM properties.

```text
-Dprogressivestages.entityPresenceFixture=true
-Dprogressivestages.entityPresenceFixtureSamples=8400
```

The collector is disabled unless the first property is present. It measures the server tick event
window and inclusive `EntityPresenceEnforcer.isPresenceDenied` time on the server thread. On a
normal server shutdown it writes
`debug/progressivestages-entity-presence-fixture.csv` in the server game directory. The CSV has one
raw row per tick followed by summary rows. The `8400` cap provides seven minutes of raw samples at
twenty ticks per second, leaving capacity for startup, a sixty second warmup, and a one hundred
twenty second comparison window. Do not enable this diagnostic in normal production operation.

## Correctness gate

With entity presence rules enabled, verify all of the following before collecting any performance
result.

1. The denied player cannot render, target, attack, interact with, or be targeted or damaged by the
   denied skeletons.
2. The eligible player sees, targets, attacks, and is targeted by the same skeleton entities.
3. Skeletons remain in the shared world for the eligible player. The denied player must not cause a
   global despawn, duplicate, or spawn cancellation while an eligible player is nearby.
4. Grant and revoke the denied player's stage between two entity decisions in the same server tick.
   The second decision must use the new stage state.
5. Change a scoreboard value and trigger a tracked entity decision in the same tick. The second
   decision must use the new scoreboard value.
6. Trigger a metric or combat session, enter and leave a structure session, change dimension,
   disconnect, reconnect, and reload the stage files. Each transition must discard the old snapshot
   before the next entity decision.

Use the focused `EntityPresenceContextCacheTest` for tuple construction and invalidation coverage.
The dedicated server scenario is still required because the focused test cannot prove client
concealment, targeting, entity lifecycle, or multiplayer tracking behavior.

## Performance gate

Run the following two captures from a clean server start. Do not compare runs with a changed JAR,
world, player count, entity population, simulation distance, warmup, sample duration, or profiler
configuration.

1. Run a rules disabled control with the same two players and entity population. Warm up the fixture
   for at least sixty seconds, then collect a server thread profile and raw MSPT samples for at least
   one hundred twenty seconds.
2. Restart from the same clean fixture. Enable the skeleton presence rule, repeat the identical
   warmup, then collect the same profile and raw MSPT samples for the same duration.
3. Calculate p95 MSPT for each run by sorting the raw MSPT samples ascending and selecting the value
   at `ceil(sample_count * 0.95)`. Calculate the percentage change as
   `(enabled_p95 - control_p95) / control_p95 * 100`.
4. In the enabled server thread profile, calculate the inclusive share of entity presence evaluation
   work. Record the profiler call tree or equivalent sampling evidence, not only a summary value.

The gate passes only when entity presence evaluation is below five percent of server thread time and
the enabled p95 MSPT is at most ten percent above the rules disabled control. A failed, incomplete,
or incomparable capture fails the gate. Do not average multiple captures to hide a failure.

## Phase 001 capture record

The paired capture used Minecraft 1.21.1, NeoForge 21.1.219, Java 21, two connected players in the
same overworld area, and 96 invulnerable persistent skeletons. The rules-disabled control and the
rules-enabled candidate each used the final 2,400 raw samples after the required 60-second warmup.
The eligible player retained the access stage. The denied player did not own it.

| Capture | Raw CSV SHA-256 | p95 MSPT | Entity presence share | Verdict |
| --- | --- | ---: | ---: | --- |
| Rules disabled | `4502589273c29d46959424aa435b2228eadca9b7a55d7b3fe7996921ee345fe4` | 10.927356 ms | 1.605524% | Control valid |
| Rules enabled | `a1e496e09a31b2299509f1a60c5deb2941273e1f4822112db7f123a6a0bceee2` | 7.058566 ms | 1.471195% | Pass |

The enabled p95 delta was -35.404630%. The entity presence share remained below the five percent
limit, and the enabled p95 was not more than ten percent above the control. The performance gate
therefore passed for this candidate capture. The live mixed-player run also verified shared entity
lifecycle, denied-player concealment, immediate grant and revoke visibility transitions, and
eligible-player visibility. Any code change to entity presence behavior invalidates this record and
requires a fresh paired capture.

The project currently registers no GameTest functions. `./gradlew runGameTestServer` completed
successfully after NeoForge reported that no test functions were available. This phase therefore
uses focused JUnit coverage together with the dedicated-server, two-client fixture for its
world-dependent verification.

## Evidence packet

The Phase 001 packet must include the candidate commit, signed artifact identity, SHA 256 and SHA
512 hashes, environment manifest, stage files, player stage states, raw samples, profile exports,
p95 calculation, entity presence share calculation, correctness assertions, focused test result,
dedicated server log, and the pass or fail verdict. Any code change after a capture invalidates the
affected correctness and performance evidence and requires a new capture.
