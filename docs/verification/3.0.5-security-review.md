The reviewed assets are stage ownership, editor drafts, server configuration and session

running inside the server process are separate trust boundaries. Source review does not establish
resistance to their concurrent filesystem changes or to malicious server payloads on a client.

## Draft synchronization findings

Alerts 146 and 147 identify `EditorApplyService.java` lines 49 and 65. They compare later
`draft.baseFiles()` and `draft.files()` reads with the earlier base file check at line 41.

The only production call to `EditorApplyService.apply` is in
[`EditorSessionService.applyReviewed`](../../src/main/java/com/enviouse/progressivestages/server/editor/EditorSessionService.java).
Its only caller is `apply`, which holds `synchronized (draft)` from the expected revision check
through validation, filesystem apply, `acceptApplied`, persistence and return. In
[`EditorDraft`](../../src/main/java/com/enviouse/progressivestages/server/editor/EditorDraft.java),
mutation, migration, undo, redo, collaborator changes and acceptance synchronize on that same
object. File accessors return copies. The two direct GameTest callers construct private drafts;
they do not expose another production call path.

**Disposition:** false positives for a concurrent draft mutation through the reviewed production
entry point, with high confidence. The caller holds the required monitor across the calls that
the alerts compare. No extra monitor or suppression was added merely to change scanner output.
Reassess these findings if another production caller is introduced or the outer lock changes.

This conclusion is distinct from filesystem concurrency. The
[external file change regression](../test/editor-external-changes.md) proves that an edit made
before apply, without a configuration reload, is detected. It does not prove that another local
process cannot edit a file after the comparison and during the transaction.

## Sensitive logging findings

| Alert | StageManager location | Reported source | Actual data |
|---|---|---|---|
| 1 | Line 928, dependency denial debug message | `ActionRegistry.java` line 54 | Stage ID used to compensate a revoke |
| 3 | Line 1808, stage change debug logging | `ActionRegistry.java` lines 43 and 54 | Stage ID used to compensate a grant or revoke |
| 5 | Line 1192, unsatisfiable dependency warning | `ActionRegistry.java` line 54 | Stage ID used to compensate a revoke |
| 6 | Line 1478, nonexistent stage warning | `ActionRegistry.java` line 43 | Stage ID used to compensate a grant |

In [`ActionRegistry`](../../src/main/java/com/enviouse/progressivestages/common/rehaul/action/ActionRegistry.java),
the grant and revoke providers parse the configured stage into a `StageId` and return it as the
successful action's compensation value. [`ActionExecutor`](../../src/main/java/com/enviouse/progressivestages/common/rehaul/action/ActionExecutor.java)
stores that value and supplies it to the matching provider's compensation method. The parameter
named `token` at each reported source is cast back to `StageId`. It is an undo value, not an
authentication token. None of these four reported flows obtains an editor session secret.

**Disposition:** false positives for credential disclosure at these four reported flows, with
high confidence. The messages contain stage identifiers and, for two messages, the player's
display name and gameplay context. Player names and progression remain operator visible log
data; this finding disposition is not a claim that logs contain no personal information.
Renaming the undo parameter or deleting useful stage warnings is unnecessary.

## Network string bounds

Alerts 80 through 95 identify sixteen no argument `readUtf()` calls in
[`NetworkHandler`](../../src/main/java/com/enviouse/progressivestages/common/network/NetworkHandler.java).
They decode `WhyLine`, `ChallengeLine` and `ChallengeHudLine`. The first two feed
`StageGuiDataPayload`; the third feeds `ChallengeHudPayload`. Both payloads are registered
with `playToClient`.

Inspection of the installed loader's `FriendlyByteBuf` bytecode shows `readUtf()` delegates to
`readUtf(32767)`. The installed Minecraft `Utf8String.read` rejects an encoded length above
`ByteBufUtil.utf8MaxBytes(limit)`, a negative length, a length above the readable buffer, and a
decoded Java string length above the supplied limit. These are enforced defaults, not an
unlimited allocation inferred from a method name.

| Inspected archive | SHA256 |
|---|---|
| `neoforge-21.1.248-server.jar` | `1808fab692dc44b2d474295d1cdd9f1fe8a7dceab4f594210873646fafdf1359` |
| `server-1.21.1-20240808.144430-srg.jar` | `26ca9c40d7e1681190b428583c38816852218e78df3f8bdb60a59a78503aec71` |

The inspection used Java 21 `javap -c` against the exact installed archives, without extracting
classes or launching Minecraft. `FriendlyByteBuf` is in the patched loader archive, while
`Utf8String` is in the Minecraft archive. An initial lookup for the latter in only the patched
archive did not find it; the successful inspection used the containing archive listed above.

**Disposition:** the literal claim that these sixteen strings lack an enforced length bound is
not supported. A tighter field specific cap would be a separate protocol decision. This result
does not establish collection bounds, total decoded payload limits, request frequency limits or
safe client behavior for every malformed payload. No codec or protocol was changed.

## Packet direction and authorization

Of the 39 registration findings, 34 belong to `playToClient` registrations. Their alert IDs are
96 through 115, 118 through 126, 129 through 131, 133 and 134. Each registration's second
directional callback is empty. These sites do not expose a client to server mutation handler.
This direction check resolves that specific server authorization hypothesis; it does not certify
all client decoders or callbacks against malformed server input.

The five actual server registrations require separate analysis:

| Alert | Entry point | Observed authority check | Remaining scope |
|---|---|---|---|
| 116 | `handleRequestStageGuiServer` | Uses the actual `ServerPlayer` from the payload context and returns that player's GUI data | Repeated request cost and data visibility policy |
| 117 | `handlePurchaseServer` | Uses the actual player, resolves the server definition, checks purchasability, cooldown and `canPurchase`, then performs the server grant | Full cost, ownership and repeated request failure matrix |
| 127 | `handleClientSnapshotAck` | Uses the actual player and accepts only the current revision and server computed checksum | Work performed before rejection and repeated acknowledgement cost |
| 128 | `handleClientSnapshotRequest` | Uses the actual player; a claimed base is checked against that player's acknowledged revision, checksum and server history | Repeated snapshot generation and response cost |
| 132 | `handleEditorRequest` | Uses the actual player and delegates to session authorization before action dispatch | Complete decoder, malformed request and resource limit coverage |

All five enqueue their work through the payload context. Their caller cannot supply another
player UUID to select the execution identity. The GUI and snapshot requests intentionally serve
ordinary players; an absent operator check alone does not demonstrate an authorization defect.

For alert 132, `EditorSessionService.handle` checks the request's UTF8 byte length against 1 MiB,
then authorizes before parsing JSON or executing actions. Authorization removes expired sessions,
binds the session to the actual player, requires current operator level 3, compares the supplied
secret hash with `MessageDigest.isEqual`, and verifies current draft ownership or collaborator
membership. The session lifetime is 30 minutes. The packet codec limits the secret to 128 Java
characters and the body to `MAX_REQUEST_BYTES` Java characters; the subsequent byte check is a
separate stricter UTF8 bound. These observations support the existing
[authorization regression procedure](../test/editor-authorization.md), not a new runtime pass.

No server registration is marked fully resolved by this direction and authorization review.
In particular, GUI generation scans the item registry and stage definitions, while snapshot
requests and acknowledgements prepare snapshot data. The inspected entry points do not contain
a dedicated request frequency guard. This is a concrete resource review target; a measured
reachable denial of service and the applicable transport limits have not yet been established.

## Editor command permission inheritance

Alerts 35 through 41 identify `status`, `sessions`, `drafts`, `resume`, `discard`, its `confirm`
child, and `revoke` beneath `/stage editor`. In
[`StageCommand.register`](../../src/main/java/com/enviouse/progressivestages/server/commands/StageCommand.java),
the parent `editor` node requires permission level 3 before any of those children can be parsed
through the registered command tree. An absent duplicate requirement on each child does not
remove the parent requirement. The `stages` and `pstages` aliases redirect to the same stage
root, retaining the `editor` node on the path.

**Disposition:** false positives for missing command permission on these seven registered
editor paths, with high confidence from the declaration and parent path. This does not resolve
the other 56 command findings, direct invocation by another in process mod, all source changing
command wrappers, or the real command provider matrix. Public `list`, `check` and `progress`
commands can target another player in the current implementation; their information visibility
policy needs explicit comparison with the product contract rather than a blanket assumption
that every public command is either safe or defective.

## Open review boundaries and cleanup

The remaining 56 command findings still need complete parent requirement and execution path analysis.
The nine path findings still need full caller and filesystem trust analysis. Lexical path
normalization alone does not establish symlink safety. Dependency advisory disposition, real
provider compatibility, browser acceptance and the remaining runtime matrix stay open.
No broad security pass or phase completion is claimed.

The audit ran read only API queries, source reads and bounded bytecode inspection on `node-1`.
It created no server, client, browser, temporary archive, extracted class, build output or test
runtime. Every inspection subprocess exited. Only this evidence document and its navigation
links are retained. Preexisting runtime libraries, the candidate, source worktrees, the immutable
goal and the active phase cursor were preserved.
