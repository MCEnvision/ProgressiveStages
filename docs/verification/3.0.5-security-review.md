## Draft synchronization findings

Alerts 146 and 147 identify `EditorApplyService.java` lines 49 and 65. They compare later
`draft.baseFiles()` and `draft.files()` reads with the earlier base file check at line 41.

The only production call to `EditorApplyService.apply` is in
[`EditorSessionService.applyReviewed`](../../src/main/java/com/enviouse/progressivestages/server/editor/EditorSessionService.java).
Its only caller is `apply`, which holds `synchronized (draft)` from the expected revision check
through validation, filesystem apply, `acceptApplied`, persistence and return. In
[`EditorDraft`](../../src/main/java/com/enviouse/progressivestages/server/editor/EditorDraft.java),
mutation, migration, undo, redo, collaborator changes and acceptance synchronize on that same
object. File accessors return copies. The two direct GameTest callers construct private drafts;
they do not expose another production call path.

**Disposition:** false positives for a concurrent draft mutation through the reviewed production
entry point, with high confidence. The caller holds the required monitor across the calls that
the alerts compare. No extra monitor or suppression was added merely to change scanner output.
Reassess these findings if another production caller is introduced or the outer lock changes.

This conclusion is distinct from filesystem concurrency. The
[external file change regression](../test/editor-external-changes.md) proves that an edit made
before apply, without a configuration reload, is detected. It does not prove that another local
process cannot edit a file after the comparison and during the transaction.

## Network string bounds

Alerts 80 through 95 identify sixteen no argument `readUtf()` calls in
[`NetworkHandler`](../../src/main/java/com/enviouse/progressivestages/common/network/NetworkHandler.java).
They decode `WhyLine`, `ChallengeLine` and `ChallengeHudLine`. The first two feed
`StageGuiDataPayload`; the third feeds `ChallengeHudPayload`. Both payloads are registered
with `playToClient`.

Inspection of the installed loader's `FriendlyByteBuf` bytecode shows `readUtf()` delegates to
`readUtf(32767)`. The installed Minecraft `Utf8String.read` rejects an encoded length above
`ByteBufUtil.utf8MaxBytes(limit)`, a negative length, a length above the readable buffer, and a
decoded Java string length above the supplied limit. These are enforced defaults, not an
unlimited allocation inferred from a method name.

| Inspected archive | SHA256 |
|---|---|
| `neoforge-21.1.248-server.jar` | `1808fab692dc44b2d474295d1cdd9f1fe8a7dceab4f594210873646fafdf1359` |
| `server-1.21.1-20240808.144430-srg.jar` | `26ca9c40d7e1681190b428583c38816852218e78df3f8bdb60a59a78503aec71` |

The inspection used Java 21 `javap -c` against the exact installed archives, without extracting
classes or launching Minecraft. `FriendlyByteBuf` is in the patched loader archive, while
`Utf8String` is in the Minecraft archive. An initial lookup for the latter in only the patched
archive did not find it; the successful inspection used the containing archive listed above.

**Disposition:** the literal claim that these sixteen strings lack an enforced length bound is
not supported. A tighter field specific cap would be a separate protocol decision. This result
does not establish collection bounds, total decoded payload limits, request frequency limits or
safe client behavior for every malformed payload. No codec or protocol was changed.

## Packet direction and authorization

Of the 39 registration findings, 34 belong to `playToClient` registrations. Their alert IDs are
96 through 115, 118 through 126, 129 through 131, 133 and 134. Each registration's second
directional callback is empty. These sites do not expose a client to server mutation handler.
This direction check resolves that specific server authorization hypothesis; it does not certify
all client decoders or callbacks against malformed server input.

The five actual server registrations require separate analysis:

| Alert | Entry point | Observed authority check | Remaining scope |
|---|---|---|---|
| 116 | `handleRequestStageGuiServer` | Uses the actual `ServerPlayer` from the payload context and returns that player's GUI data | Repeated request cost and data visibility policy |
| 117 | `handlePurchaseServer` | Uses the actual player, resolves the server definition, checks purchasability, cooldown and `canPurchase`, then performs the server grant | Full cost, ownership and repeated request failure matrix |
| 127 | `handleClientSnapshotAck` | Uses the actual player and accepts only the current revision and server computed checksum | Work performed before rejection and repeated acknowledgement cost |
| 128 | `handleClientSnapshotRequest` | Uses the actual player; a claimed base is checked against that player's acknowledged revision, checksum and server history | Repeated snapshot generation and response cost |
| 132 | `handleEditorRequest` | Uses the actual player and delegates to session authorization before action dispatch | Complete decoder, malformed request and resource limit coverage |

All five enqueue their work through the payload context. Their caller cannot supply another
player UUID to select the execution identity. The GUI and snapshot requests intentionally serve
ordinary players; an absent operator check alone does not demonstrate an authorization defect.

For alert 132, `EditorSessionService.handle` checks the request's UTF8 byte length against 1 MiB,
then authorizes before parsing JSON or executing actions. Authorization removes expired sessions,
binds the session to the actual player, requires current operator level 3, compares the supplied
secret hash with `MessageDigest.isEqual`, and verifies current draft ownership or collaborator
membership. The session lifetime is 30 minutes. The packet codec limits the secret to 128 Java
characters and the body to `MAX_REQUEST_BYTES` Java characters; the subsequent byte check is a
separate stricter UTF8 bound. These observations support the existing
[authorization regression procedure](../test/editor-authorization.md), not a new runtime pass.

No server registration is marked fully resolved by this initial direction and authorization
review. At that point, GUI generation scanned the item registry and stage definitions while
snapshot requests and acknowledgements prepared snapshot data without a dedicated frequency
guard. The snapshot defects subsequently demonstrated and repaired are recorded below. GUI
request cost and applicable transport limits remain separate review targets.

[`DefaultShowcaseStages.files`](../../src/main/java/com/enviouse/progressivestages/server/loader/DefaultShowcaseStages.java)
constructs a fresh unmodifiable map from its private template list. The two production default
writers do not receive stage creation command arguments. The separate `StageCommand.newStage`
handler requires operator level 3, rejects `.` and `..` path segments, and normalizes and checks
the destination against the stages root before writing its three fixed package filenames.

For migration, [`LegacyMigrationService.plan`](../../src/main/java/com/enviouse/progressivestages/server/migration/LegacyMigrationService.java)
requires a regular source lexically inside the stages root. The command chooses that source from
the discovery result rather than interpreting the command's stage selector as a file path.
`safeDirectory` replaces the stage namespace separator and slashes with underscores. The write
operation checks the source checksum before creating the backup. Rollback additionally checks
the original file checksum and containment of both paths read from its backup metadata before
deleting or restoring anything. `MigrationPlan` is a public in process record, but the reviewed
commands do not deserialize one from player input. Arbitrary code calling that API is a separate
trust boundary, not evidence of a remotely constructible migration plan.

For editor paths, [`EditorPaths.normalize`](../../src/main/java/com/enviouse/progressivestages/server/editor/EditorPaths.java)
rejects absolute paths, normalized parent escapes, dot prefixed input and non TOML filenames.
Every draft mutation uses it. Import validates every filename before the first mutation and
rejects colon containing paths and normalized duplicates. `EditorDraftValidator` restricts the
configuration file set to the main TOML or paths beneath `stages/`, with containment checked
again inside its isolated validation directory. Apply holds the draft monitor while using those
results. Its base comparison also prevents a tampered persisted base map from silently becoming
the recovery source for a different live file set.

Editor rollback reads the changed file list from the server written audit record; a request
selects a transaction, not a new list of target paths. Each target passes `EditorPaths.normalize`
before copy or deletion. The separate rollback command requires level 3 and explicit `confirm`;
the editor action first passes the session checks documented above.

**Disposition:** the nine alerts do not establish attacker controlled lexical traversal through
the reviewed game and editor entry points. Three are fixed filename or test helper patterns;
the other six have upstream or local controls described individually above. This source review
does not establish safe behavior for hostile local filesystem changes. `Files.walk` does not
follow directory symlinks by default, but the inspected `isRegularFile`, read and copy operations
do not consistently use `NOFOLLOW_LINKS`. A preexisting symlink, a concurrent local replacement
or altered server backup metadata must not be described as covered by lexical containment.
No destructive filesystem experiment or broad path rewrite was performed.

The existing `EditorDraftTest.rejectsEscapingAndNonTomlPaths` checks a parent escape and a
JavaScript filename. The [package import regression](../test/editor-import.md) covers additional
request paths and atomic rejection. These are bounded existing tests, not proof of symlink or
concurrent filesystem resistance; neither suite was rerun for this documentation only review.

## Snapshot chunk admission limit

Source `7b99df1d62bffe31c4262b498082ea5e31644a99` enforces the existing compressed size bound
while a client snapshot is incomplete. The remote server supplies the manifest and chunk stream;
these payloads are registered only toward clients. This finding does not establish a client to
server privilege escalation. It concerns client resource use with an inconsistent remote stream.

The manifest permits at most 4096 chunks. The wire decoder caps each chunk at 24 KiB and the
assembler rejects declared compressed sizes above 16 MiB. Previously, the assembler stored every
unique chunk before comparing their combined length with the declared size. Those independent
limits permitted up to 96 MiB of retained chunk data despite a declaration of at most 16 MiB,
followed by additional assembly buffers. That upper bound follows from the verified constants;
the regression intentionally avoids making a large allocation.

The new regression announces 4096 chunks with a three byte compressed size, accepts a two byte
chunk, repeats it, sends an unrelated revision, and then supplies two more unique bytes. On the
previous assembler it failed because the excess chunk was accepted. The repair checks each new
chunk against the remaining declared byte count before adding it to the candidate. Duplicate
sequences return before copying or accounting their data. The counter uses subtraction from a
validated maximum, so cumulative addition cannot overflow past that bound. Existing final size,
decompression and checksum checks remain in place. This limits retained unique chunk bytes,
not total JVM memory or the allocations used to receive, combine and decompress them.

## Loader admission and collection boundaries

This read only inspection used the unchanged production archives on September 13, 2026. It
completes the source trace for direction, negotiation and scheduling before the five server
handlers; it does not establish a packet flood or fragment reassembly safety result.

|---|---|

`PayloadRegistrar` defaults to `HandlerThread.MAIN` and wraps handlers with
`MainThreadPayloadHandler`. Its wrapper submits the callback through the payload context.
ProgressiveStages does not change that thread selection. This agrees with the
[versioned registration documentation](https://docs.neoforged.net/docs/1.21.1/networking/payload/).
Scheduling on the main thread is not a request frequency limit or proof that expensive work is
bounded before scheduling.

`NetworkRegistry.getCodec` rejects a registered payload received on the wrong direction or
outside its registered protocol. The server `handleModdedPayload` path disconnects when payload
setup is missing, the negotiated or accepted channel is absent, or the registration cannot be
resolved. It constructs the server context from the actual listener and packet. These checks
support the existing conclusion that the clientbound registrations do not expose their client
callbacks as server mutation endpoints. They do not replace the editor's session authorization
or the purchase handler's ownership, affordability and stage checks.

The named `ServerboundCustomPayloadPacket.MAX_PAYLOAD_SIZE` value is 32767, and its clientbound
counterpart is 1048576. In these patched classes, those constants feed the discarded payload
fallback. `CustomPacketPayload` first resolves registered codecs through `NetworkRegistry` and
calls them directly. Consequently, the named constants and the general documentation alone
are not proof that every registered mod payload has those total size limits. The normal frame
decoder rejects a length wider than 21 bits. The inspected compression decoder enforces its
8 MiB advertised decompressed size check only when validation is enabled. Those are distinct
boundaries and do not prove the aggregate size of a fragmented message.

`ServerConnectionListener` selects `RateKickingConnection` only when the configured rate is
positive. `DedicatedServerProperties` defaults `rate-limit` to zero. The rate kicking connection
compares average received packet frequency once per second, then disconnects and disables reads
on excess. No deployment setting was changed. This mechanism cannot be counted as an enabled
default admission budget, and a packet frequency setting alone does not prove a byte budget.

NeoForge also installs its negotiated generic packet splitter in both directions. Its separate
fragment receive path precedes application payload handling. The inspected code does not supply
an aggregate receive budget that this review can credit. Fragment reassembly therefore remains
a loader dependency review item. No loader patch, version change, public upstream report or
network stress test was performed. This observation does not invalidate the demonstrated local
snapshot byte accounting repair, whose boundary begins after payload decoding, but that repair
cannot be presented as protection for every lower transport layer.

For the client collection hypothesis, `ByteBufCodecs.collection` without an explicit maximum
uses `Integer.MAX_VALUE`, while its decoder caps the initial collection capacity at 65536. It
then decodes each element from the buffer. A huge count alone therefore does not immediately
allocate an array of that count. This resolves that specific initial allocation hypothesis;
it does not prove a total list size or CPU limit, and no broad malformed client payload result
is inferred. The existing application string and snapshot bounds remain separate controls.
