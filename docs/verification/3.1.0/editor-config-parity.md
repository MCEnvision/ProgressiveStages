# Editor configuration parity

## Scope and evidence level

This record preserves the baseline inventory and pre-fix reproduction from P002-TASK-007, and records the implementation and static verification completed for P002-TASK-008. Baseline source observations are pinned to commit `6501942f6fe8c2acf212f2f5e8c4a61b72fe40e1` on `envy/3.1.0-phase-002` in the verified `node-1` checkout. Current implementation evidence refers to the uncommitted candidate in that same checkout. Source and unit test results do not prove a running server, browser or client.

The earlier player guide report names candidate commit `18c7d37`. Its build and runtime results are historical and do not verify this candidate.

The sponsor's old save shape was reproduced through the production `RulesPanel`. Adding `mod:immersiveengineering` to a legacy stage emitted `[ores].locked = ["mod:immersiveengineering|priority=100"]`. The captured bytes have SHA 256 `6c92e3bcf6918d46c05d95c46f5bbe28a1520b527b55e7aa029f676a35e0b316`. A Java 21 test consumed those same bytes through `StageFileParser.parseText`. Parsing succeeded, but `LockDefinition.oreOverrides()` was empty. The save was valid TOML and a no operation in the old ore override path. The repaired editor now writes canonical `[[blocks.overrides]]` data, while retaining `[[ores.overrides]]` as an alias. This baseline reproduction does not claim the reporter's exact game environment was reproduced.

The form disables its action selector for legacy category lists but initializes it from the first displayed action. This still presents a false action for blocks, fluids, enchants, crops, trades, brewing and other fixed-action differences. The legacy path also appends an inline priority annotation to every selector, although ordinary `LegacyStageCompiler.addCategory` resolves category restrictions through the stage priority. Its per-selector priority UI therefore does not represent the effective priority for those legacy lists. Structure priority is a separate implemented cascade.

## P002-TASK-008 implementation and static evidence

The generic ore lock path is now a dedicated Block overrides editor form. It writes `[[blocks.overrides]]`, supports one `target` or a `targets` list, and accepts exact block IDs, block tags and mod namespaces, including the `tags:` alias. Show as values are checked as blocks, drop values as items, and selector and row priorities are retained. Existing `[[ores.overrides]]` tables reopen through the same editor and Java resolution path. Targeted edits keep comments and unrelated source intact. The encryption shortcut uses the same selector expansion and does not create a second mapping.

`StageFileParser` rejects ineffective `[ores].locked`, `[ores].always_unlocked` and `[ores].allowed` fields with an actionable hint. It preserves the source table and field for diagnostics. The registry expands and deduplicates configured targets at stage registration, orders overrides by priority with stable tie breaks, uses an indexed block lookup, and clears that index on reload. A selector that matches no registered blocks reports its exact source field and a zero match count. The new registry unit test covers exact ID and mod selectors, ordering, attribution and index clearing. Bare JUnit does not load the complete vanilla block tag data, so real tag membership and modded registry expansion remain part of P002-TASK-009 runtime proof.

The adjacent mapping fixes use each legacy category's actual parser key and fixed action instead of emitting generic keys the parser ignores. The UI no longer offers ineffective legacy priority, unsupported selector forms or generic effects without the required replacement metadata. Screens use the menu catalog, and categories with specialized keys route to those keys. `[blocks].locked` remains a separate placement and interaction rule. The editor and documentation explain that a block override changes display and drops, not whether block placement is allowed. Unsupported source remains available instead of being silently rewritten.
