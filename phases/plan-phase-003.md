## Purpose and Ownership

This phase proves that the production editor, server-authoritative inventory transaction path, in-game progression map, and exact 3.0.4 candidate artifact deliver the user-visible behavior assigned to CORE-PHASE-003. It owns CORE-REQ-005, CORE-REQ-006, CORE-REQ-007, CORE-REQ-011, and CORE-REQ-012 only. Its measurable outcome is a candidate JAR whose embedded and served editor bundle can round trip every supported enchantment restriction, whose recipe-output control selects an output item and persists it through exact `[recipes].locked_items` semantics, whose separate exact-recipe control persists only `[recipes].locked_ids`, whose canonical `[[interactions]]` `item_into_inventory` rules preserve paired source-item and destination selectors and deny matching player-initiated insertions without mutation, item loss, duplication, ghost state, or automation regressions, whose category overlay remains above stage icons without breaking map interaction, and whose shipped resources contain every other previously advertised 3.0.3 capability that the integrated CORE-PHASE-000 audit proved missing.

The master plan owns the product boundary, requirement definitions, phase order, and release endpoint. This blueprint owns the dependency-ordered implementation and proof for CORE-PHASE-003. It may correct a capability only when a CORE-PHASE-000 audit row links the missing behavior to a public 3.0.3 promise and an inspected shipped artifact. It does not authorize a novel feature beyond the explicitly owner-promoted CORE-REQ-012, a platform upgrade, a schema redesign, or work assigned to another phase.

## Scope Boundaries

### Included Scope

- CORE-REQ-005: verify the production Easy Builder workflow for creating, editing, removing, validating, saving, reopening, and compiling every supported enchantment restriction, and repair only the failed surfaces.
- CORE-REQ-005: prove that visual form state and TOML source round trip to the same normalized runtime rule, including field-specific rejection before apply.
- CORE-REQ-005: prove that the production editor resources used in testing are byte-identical to the resources embedded in and served by the exact candidate JAR, and repeat the applicable browser workflow after final candidate packaging.
- CORE-REQ-006: reproduce or artifact-verify category menu layering, then repair render depth and input precedence when the overlay is open.
- CORE-REQ-006: preserve pan, zoom, search, category selection, navigation, inspector behavior, and focus after the overlay closes or a category is selected.
- CORE-REQ-007: correct only a user-visible 3.0.3 capability with a completed CORE-PHASE-000 matrix row that identifies the public promise, inspected artifact, observed absence, and required runtime workflow.
- CORE-REQ-007: reconcile corrected behavior with final artifact inventory and documentation that the candidate JAR proves.
- CORE-REQ-011: make the visual builder present distinct user intents. Selecting an output item serializes only `[recipes].locked_items`; selecting an exact recipe identifier serializes only `[recipes].locked_ids`; generic `[recipes].locked` is rejected or migrated only when its intent is unambiguous, and is never persisted as a successful ambiguous rule.
- CORE-REQ-011: prove create, edit, remove, save, reopen, TOML source, review, operator apply, persisted-file reload, client synchronization, parser and compiler normalization, and runtime recipe enforcement against the production editor bundle and candidate JAR.
- CORE-REQ-011: migrate a safely recognizable legacy generic recipe lock atomically or reject it with a field-specific error, preserving the last valid draft, persisted stage file, compiled rule set, synchronized client state, and runtime behavior.
- CORE-REQ-012: add the canonical `[[interactions]]` entry with `type = "item_into_inventory"`, `held_item`, `target_kind`, `target`, `effect`, and `priority`, while leaving every existing interaction type and field unchanged.
- CORE-REQ-012: compile the source and destination as one paired decision. Both axes use the existing `all:*`, `id:`, `mod:`, `tag:`, `name:`, and `#` selector grammar, including broad rules with narrower priority allows or exclusions and the existing safe equal-priority tie policy.
- CORE-REQ-012: resolve authoritative block, registered menu type, and stable inventory-owner identities through a bounded server resolver registry and extension point that supports contributed tags and editor catalog entries without a hard dependency.
- CORE-REQ-012: classify standard click, quick move, quick craft, hotbar swap, and pickup-all transactions by actual insertion direction, then accept or deny each complete transaction before observable mutation or irreversible side effects and resynchronize an authoritative pre-transaction state after denial.
- CORE-REQ-012: preserve playerless hopper, pipe, capability, and machine insertion behavior. Only an authenticated `ServerPlayer` supplied by the server transaction or registered integration origin may enter the gated path, never a player inferred from proximity, ownership, client data, or last opener state.
- CORE-REQ-012: expose complete Easy Builder and TOML source workflows with separate source and destination controls, target-kind selection, selector modes, catalog-backed autocomplete, priority exceptions, field-specific validation, and explain diagnostics, then prove packaged-bundle and final-JAR behavior.

## Architecture and Implementation Boundaries

The visual editor is an authoring surface, not an authority boundary. Easy Builder controls translate user choices into the existing canonical stage representation. TOML source and the visual form must normalize to the same compiler input, and the server must validate operator permission and the complete draft before mutation. A visual control cannot introduce a second enchantment model, silently drop unknown supported fields, or apply partially valid state. Field errors must identify the rejected field before apply while retaining the last valid draft for correction.

Recipe locks follow the same single-model boundary. The classic visual builder maps a recipe-output selection to exact `[recipes].locked_items`; it maps a recipe-identifier selection to the separate `[recipes].locked_ids` collection. The serializer, TOML source view, parser, draft validator, compiler, persisted stage-file reload, client synchronization, and runtime enforcement must agree on that distinction. Generic `[recipes].locked` is invalid as a successful persisted recipe-lock field. If an existing generic value is unambiguously convertible, migration must validate the complete converted draft and replace it atomically. If it is missing type information, ambiguous, or invalid, apply must fail with a field-specific result and preserve the last valid draft, persisted file, compiled rules, synchronized client state, and active runtime behavior.

Inventory insertion gating extends the same canonical interaction model. An entry uses `type = "item_into_inventory"`, `held_item`, `target_kind`, `target`, `effect`, and `priority`. `held_item` resolves the actual stack that would enter the destination, not merely the clicked or carried stack. `target` resolves the receiving inventory through its declared target kind. Both selectors retain the existing matcher grammar and remain inseparable throughout serialization, validation, normalization, compilation, decision caching, explain output, and runtime enforcement. No step may widen one axis into an independent rule. Existing interaction types, `target_block`, `target_entity`, selector behavior, and recipe-lock keys remain unchanged.

`InventoryTargetResolverRegistry` is a logical-server boundary and a stable extension point. A block-backed inventory resolves to a registered block ID, a menu-backed inventory resolves to a registered menu type ID, and an inventory-backed target resolves to a stable built-in or registered owner ID and contributed tags. Resolver and catalog identities must be the same namespaced contract. Serialized target identity must not depend on display text, translated text, client claims, Java class names, object identity, coordinates, last opener, owner metadata, or nearby players. Resolution must be bounded and deterministic, avoid broad registry scans in hot paths, and surface absent, ambiguous, or unsupported targets through bounded diagnostics.

The logical server owns the complete player transaction. The enforcer receives an authenticated initiating `ServerPlayer`, authoritative menu and slots, the current compiled rule snapshot, the candidate source stacks, and server-resolved destination identities. It computes resulting transfer direction across all touched slots before any observable mutation or callback. Standard click, quick move, quick craft, hotbar swap, and pickup-all paths are covered by resulting insertion, not by click-name blocklists. Removal-only operations remain unchanged unless another existing rule denies them. A matching denied transaction must preserve every source and destination slot, carried and hotbar stack, count, menu state ID, and authoritative client view, and must not emit crafting, trade, advancement, sound, statistic, callback, or external inventory effects. If the repository cannot establish a pre-mutation hook for a path, a fallback is admissible only after proving complete rollback occurs before irreversible side effects; otherwise the path blocks phase exit.

Player origin is explicit. Vanilla or supported menu transactions provide their authenticated server player. A registered server-side integration may provide a real `ServerPlayer` through the extension contract. Hopper, pipe, capability, machine, and other playerless transfers never enter the rule path, even when a player is nearby or owns, opened, or recently used the inventory. Concurrent players sharing one menu or inventory evaluate against their own stage state and the same authoritative contents without cross-player decision reuse. Rule reload swaps a complete compiled snapshot atomically, and an already-open menu uses the new snapshot on its next transaction.

Easy Builder and TOML source are equal authoring surfaces for inventory insertion rules. The visual action must expose separate source and destination selectors, target kind, effect, priority, conditions, and exceptions. Item, block, menu, and inventory-owner autocomplete derive from the stable catalog projection, and stale or unsupported entries remain explicit validation errors rather than silently changing identity. Create, edit, duplicate, remove, review, apply, reopen, reload, and explain workflows must preserve exact semantics. The editor never supplies an authoritative runtime destination or player identity.

The production-bundle boundary is part of correctness. Source-level browser tests are necessary but insufficient. The verified resources must be the resources embedded in and served from the candidate JAR. Bundle identity must be recorded with the candidate source revision and artifact hash so later phases can detect stale or mismatched frontend output.

`StageTreeScreen` remains client-only presentation. The category overlay must be composed and clipped in a layer that visually covers nodes within its bounds. While open, it must receive pointer events before map nodes, prevent click-through, and define predictable close and selection behavior. When it closes, map pan, zoom, search, navigation, category state, focus, and inspector interaction must remain usable. The chosen rendering technique must follow the existing client architecture and must not cause client classes to load on a dedicated server.

Artifact-parity corrections are evidence gated. CORE-PHASE-000 supplies the claim, inspected artifact, and observed gap. This phase may restore the established contract but may not broaden it. Public identifiers, TOML keys, stage schema, commands, packets, persistence, and API signatures remain stable unless the public 3.0.3 contract already requires the exact missing form and a compatible correction is proven. Any unavoidable compatibility change is a plan conflict and blocks work rather than authorizing local redesign.

Client render and input paths must avoid per-frame full registry, stage, or entity scans. Menu transaction paths must avoid per-click full registry, stage, resolver, or slot-space scans beyond the slots participating in the authoritative transaction. Resolver lookup and compiled decisions must use stable indexed state suitable for the existing server-thread model. Editor serialization must be deterministic for equivalent normalized inputs. Tests must avoid private credentials and sanitize operator URLs, local paths, confirmation codes, and server data from stored evidence. No phase output authorizes release or external publication.
