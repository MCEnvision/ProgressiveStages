## Purpose and Ownership

This phase proves that the sequentially integrated and signed outputs of CORE-PHASE-001, CORE-PHASE-002, and CORE-PHASE-003 preserve ProgressiveStages compatibility and regression safety before release integration begins. Its sole canonical requirement is CORE-REQ-008. The phase owns the compatibility matrix, security and authority checks, client, integrated-server, dedicated-server, and multiplayer runtime exercises, optional-mod combinations, artifact inspection, failure routing, recovery rehearsal, and completion evidence for the supported ProgressiveStages 3.0.4 patch boundary. That matrix consumes the integrated CORE-REQ-011 recipe-lock result and CORE-REQ-012 inventory insertion result delivered by CORE-PHASE-003 without reassigning ownership or implementation of either upstream requirement.

The sole upstream phase dependency is CORE-PHASE-003. CORE-PHASE-001 and CORE-PHASE-002 remain required transitive evidence inputs carried through the signed sequential integration chain, not additional phase dependencies.

The master plan owns product scope, supported behavior, architecture, phase order, and the release endpoint. This blueprint owns only execution of CORE-PHASE-004. It does not reopen the individual fixes from earlier phases. Any failed check that points to an earlier phase-owned defect blocks this phase and routes a corrective change back to the owning component before the affected verification is rerun.

## Architecture and Implementation Boundaries

The logical server remains authoritative for stage membership, rule decisions, configuration reload, permissions, persistence, and enforcement. Client state is presentation or synchronized cache state only. Compatibility proof must reject any path where a client request mutates authoritative state without server-side operator authorization, payload validation, bounds validation, and execution on the correct logical thread.

This phase does not prescribe new implementation. It verifies that the integrated candidate preserves dependency direction: common and server code cannot load client classes, core startup cannot load absent optional integration classes, and optional adapters cannot own stage policy. An unavailable Curios, JEI, or EMI adapter may remove only that integration's behavior. It must not crash core startup, make a denied action permissive, alter saved state, or contaminate another installed adapter. Client verification must use the packaged candidate and cover the progression map, inventory entry button, editor launch, recipe-viewer integration, synchronized caches, GUI scaling, render depth, pointer and keyboard routing, pan, zoom, search, category selection, owned filtering, inspector or detail state, and clean disconnect without treating screenshots alone as behavior proof.

Compatibility fixtures must be copied before execution. Tests may mutate only disposable copies. Stage identifiers, `pack:stage` parsing, TOML fields, configuration keys, commands, API contracts, persisted stage ownership, and network behavior remain stable unless the master contract explicitly documents a compatible default. No test may repair a fixture in place and then claim backward compatibility.

Recipe-output and exact-recipe locks remain separate schema concepts. `[recipes].locked_items` selects recipe outputs, while `[recipes].locked_ids` selects exact recipe identifiers. The integrated candidate must not serialize either concept through the generic `[recipes].locked` field or silently translate one canonical field into the other. Compatibility handling for a legacy editor draft is permitted only at the editor transaction boundary: an unambiguous draft may migrate to `[recipes].locked_items`, while an ambiguous or invalid draft must fail with a field-specific result before the live file, compiled snapshot, or synchronized runtime state changes.

The compatibility path must exercise one atomic transaction from production Easy Builder visual form through canonical TOML, validation, backup, persistence, reload, compilation, synchronization, runtime enforcement, and editor reopen. A failure at any step preserves or restores the previously verified file and compiled state. Successful application must be observable both as denial for a player lacking the stage and normal recipe behavior for an eligible player. Source-level serializer evidence alone does not satisfy this boundary.

The integrated inventory-insertion path uses the same server-authoritative compatibility boundary. The source selector resolves the stack entering the destination, while the destination selector resolves only from authoritative block IDs, registered menu type IDs, or stable inventory-owner identities and tags supplied by built-in or registered resolvers. Compatibility proof must show that vanilla chest and furnace selection, explicit player-inventory selection, a supported custom menu, and a registered modded resolver extension produce stable, distinct destination identities. Display text, Java class names, coordinates, proximity, last opener, ownership metadata, and client-supplied identities are never accepted as serialized destination or player-origin authority.

Every supported player insertion path is classified by resulting transfer direction, not click name. Standard click placement, quick move or shift click, quick craft or drag across multiple destination slots, hotbar-number swap, and pickup-all or double-click must be accepted or denied as coherent transactions. Removal-only controls must remain allowed unless another existing rule denies them. A denied transaction must leave all involved slots, carried and hotbar stacks, counts, menu state ID, total inventory count, and synchronized client view equal to the recorded pre-transaction state. No crafting, trade, advancement, sound, statistic, resolver callback, capability callback, or external inventory side effect may run. A rollback path is acceptable only when these full equivalence and no-side-effect assertions prove it safe.

Playerless hopper, capability, pipe, machine, and equivalent automation keeps existing behavior. Only the vanilla authenticated menu flow or a registered server-side extension that supplies the actual initiating `ServerPlayer` may enter the player-gated path. Mixed-stage players using the same container must receive isolated decisions against one authoritative shared inventory. Atomic rule reload must update an already-open menu on its next transaction, and a rejected rule must preserve the prior persisted file and compiled snapshot through reconnect and server restart.

Runtime evidence must distinguish integrated and dedicated servers. Dedicated-server startup proves client isolation. Multiplayer scenarios must use server-authoritative state for two concurrently connected players and cover disconnect, reconnect, synchronization, and clean lifecycle transitions. Concurrency checks must identify the server thread mutation boundary and detect stale state rather than masking it with arbitrary waits.

Security evidence must cover permission denial, malformed input, unsupported identifiers, size and bounds validation where applicable, path safety for editor-managed files, and sanitized diagnostics. It must not capture secrets, confirmation codes, private raw logs, or unrelated player data. Static review includes dependency provenance already required by EXT-001 and verifies that no hard optional dependency or unauthorized network mutation was introduced.

All evidence is revision-bound. A change to Java source, resources, generated assets, dependencies, Gradle metadata, mod metadata, editor bundle, or documentation that affects a claimed behavior invalidates the corresponding checks. The invalidation ledger defines the minimum rerun set; uncertainty requires rerunning the complete phase. Final-artifact evidence must come from the built JAR installed into clean client and dedicated-server instances, not a development run configuration or source resource directory. The artifact record binds the JAR filename, source commit, byte size, SHA-256, SHA-512, embedded mod metadata, packaged editor asset digests, and required classes and resources before any smoke workflow begins.
